# MACS J1752: redshift provenance for a nearby cataloged radio source

The [previous catalog check](../macs1752-patch-catalog/README.md) found radio source ILTJ175159.28+443849.6 about 5.29 arcseconds from the selected T50 − T50SUB difference peak. The LoTSS DR2 value-added catalog v1.1 associates an optical position with that radio source and gives `z_best = 0.3469112`. A targeted read of the **original full catalog row** reveals `z_source = Phot`, `zphot = 0.3469112`, `zphot_err = 0.0308101`, and `flag_qual = 1`. The [catalog documentation](https://www.lofar-surveys.org/public/DR2/catalogues/README-v1.1.md) defines that error as a predicted 1σ photometric-redshift uncertainty and the flag as a quality classification. SDSS, DESI and HETDEX spectroscopic-redshift fields in this v1.1 row are blank; this does not prove spectroscopy is unavailable elsewhere or in later catalog versions.

[Della Chiesa et al.](https://arxiv.org/html/2604.02410) give the cluster redshift as 0.366. That value lies within the catalog's reported photometric 1σ range for the associated object, but this does **not** establish cluster membership, source identity, or the physical origin of the difference patch. The catalog reports a 9.14-arcsecond separation between its radio and optical positions and lists `Position_from = Ridge line code`; the radio source is extended, so a simple nearest-coordinate assumption is insufficient. Optical association confidence, independent astrometry and spectroscopy still need examination. The value-added catalog's [methodology](https://arxiv.org/html/2309.00102#S8.SS1) describes how it chooses photometric or spectroscopic `z_best`; the two-catalog radio match is a positional association, not a proof that the catalog source causes the image difference.

## Bounded retrieval and reproducibility

The official v1.1 FITS catalog is approximately 3.93 GB. We used two verified HTTP byte-range requests, retrieving only its first 51,840 header bytes and one 944-byte row. A VizieR record number suggested the row offset but **was not treated as a source ID**: the original FITS row's `Source_Name` and coordinates were checked against the targeted VizieR result. Exact ranges, source URL and SHA-256 digests are in `manifest.json`. The source could change; never reuse an old offset without checking response range, version, row identity and coordinates.

Run `python research/macs1752-photoz-provenance/analyze.py /path/header.bin /path/row.bin` with NumPy and Astropy. It validates both ranges, reconstructs a one-row FITS file in memory and checks the source identity, photometric type and coordinates. The retrieved ranges and analysis are stored privately in Azure. Cite [Hardcastle et al.](https://arxiv.org/html/2309.00102) and the [LoTSS DR2 release](https://lofar-surveys.org/dr2_release.html). No email was sent.

A subsequent [v1.2 row check](../macs1752-photoz-v12/README.md) also finds a photometric redshift and a blank DESI field for this source.
